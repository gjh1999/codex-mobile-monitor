五万人同时在线意味着多少负载

将“几万人”按峰值同时在线的自然人数规划。同一人的多个网页或设备会建立多个连接。注册席位决定账户、历史和存储规模，在线人数决定连接量，正在执行的任务数决定算力。以下参数用于生成负载和核算成本，均待试点校准。

负载满规模场景的计算口径约束的资源
长连接50,000 人 × 1.2 个前台连接 + 15,000 台在线代理 = 75,000 条。代理每 30 秒心跳一次，均匀摊开约 500 次/秒。网关套接字、直接内存、TLS 握手和重连速率。
业务 API每人平均每 10 秒读一次、每 100 秒写一次，得到 5,000 读/秒、500 写/秒。写入含任务提交，设备心跳和事件扇出另计。API 实例、缓存命中率、数据库连接池、锁等待。
状态推送2,000 条状态事件/秒 × 平均 5 个订阅者 × 1 KiB，约 9.8 MiB/s 净载荷。单个热门任务若有 1 万观察者，每秒更新两次，仅此任务就约 19.5 MiB/s。网关出口与慢客户端缓冲。日志、TLS 和重传另计。
执行槽位假设峰值每秒提交 30 个同规格 CPU 作业，平均执行 30 秒，稳定到达时平均有 900 个在跑。按 70% 目标占用约需 1,286 个槽位。GPU 按型号、显存和真实作业时长单独估算。槽位按 CPU/内存请求装箱到机器。模型账号额度、排队上限独立核算。
大对象传输400 台设备在 60 秒内各取 64 MiB，平均约 427 MiB/s。另计上传、跨区复制和失败重传。对象存储出口、客户网络、租户流量成本。

分三档验收。 首批租户用 1,000 人在线验证单个部署单元，再以 10,000 人验证热点项目和单区故障，最终在相同负载配比下压到 50,000 人。每档记录租户数、最大租户占比、设备数、对象大小、任务时长和机器规格。

存储账单也要从写入量反推。 作上界估算，若每秒 2,000 条事件持续一整天且每条落盘 1 KiB，每天约 1.728 亿条、165 GiB 原始载荷，另有索引、副本与备份。工程上将审批、控制权变更和终态逐条持久化，将高频进度合并成有游标的检查点，详细日志分片进对象存储。试点测出峰均比及各类事件占比后，再确定在线保留期和冷热存储预算。

从入口到执行节点

首版把身份、项目、任务、审批、快照和用量放在一个模块化 Java 应用中，共用本地数据库事务。长连接网关与异步处理进程独立部署，三者可以分别增减实例。按租户路由到一组拥有独立数据库和队列的服务实例，下文称为部署单元。

租户、权限与商业运营

组织付费并拥有成员和项目。每个工作区属于一个项目和一个租户，线程、设备授权、审批、归档对象都带相同边界。同一个人可以加入多家公司，每个会话明确当前组织。客户可购买席位、托管并发槽、存储和流量；自有执行节点单独计量。

  • 成员与设备分别认证。 用户经 OIDC 登录，企业可接自己的身份提供商。浏览器使用短期会话与写请求防伪保护。设备通过一次性配对换取可轮换的设备身份，限定租户、项目和执行能力。客户的模型登录及 Git 凭据保存在其授权执行端。
  • 按操作授权。 观察者可看授予的任务，开发者可提交和操作自己的工作区，审批者按项目和风险范围决定，组织管理员管理成员和套餐。私人会话默认只对所有者可见，成员加入共享项目不自动获得他人的原始对话。
  • 每一层都带租户上下文。 服务从已验证身份导出租户，复核项目成员关系；数据库用复合外键和行级安全策略，连接池在每个事务设置租户，应用角色受策略约束。缓存键、队列消息、对象前缀、检索索引与订阅鉴权采用同一范围。成员离职时撤销会话和设备授权、关闭相关订阅，后续读取再查权限。PostgreSQL 行级安全
  • 从用量到账单。 套餐服务管理席位上限与执行并发；提交时原子预留预算，完成后按事件 ID 结算实际执行秒数、存储字节时和出口字节。取消释放预留，结果未知时暂挂对账。账单保留价格版本、账期、调整记录，客户可以按项目导出明细。第三方模型只展示有来源的额度和 token。
  • 可运维、可退出。 自助完成组织创建、成员邀请、设备配对和第一条任务；企业可选专用部署单元和自有对象存储。项目配置保存区域、允许上传的数据类别和保留期。退租流程支持授权导出、撤销凭证、清理在线数据及索引，并记录备份到期日。客服访问须限时授权并留审计记录。

同一项目，谁可以写

甲、乙可以同时打开同一个项目，各自在独立 Git 工作树和线程开发；丙在 iPhone 查看两人的共享任务。甲把自己的线程从笔记本交给台式机时，只转移这条线程和对应工作区的写入权。项目级夜间自动化仍遵从原方案的人工优先规则。

同时发生的事控制规则与用户可见结果
两人接管同一线程中心事务按租户、线程和目标工作区锁定写入记录，发出递增代号。设备在发送命令、批准工具和发布结果前核对有效代号与本机原生锁。竞争失败方收到 HTTP 409、当前持有者和刷新入口，可继续观察或申请交接。
手机和桌面同时批准审批绑定原执行连接、请求 ID、实际命令、目录、设备和有效期。条件更新将 pending 改为 decided，只接受一次决定；相同幂等键返回第一次结果。代理只在原请求存活时发回执，确认前界面显示“已决定，等待执行端确认”。
IDE 打开时自动任务在跑按项目登记的 IDE / 人工 CLI 活动立即阻止新的后台推进和自动审批。已有动作到安全点后交还，前台发起的作业继续。最后一个窗口退出后核对所有设备、未决指令及原生进程，再恢复夜间策略。失联的持有者进入待核对状态。
离线重连或热门任务共享任务事件按资源生成单调序号，订阅带最后已确认序号；缺页或超过保留期时读授权快照再接增量。网关定时比较高水位，合并进度和日志推送，给每连接设字节上限。慢客户端可重连补读，审批、终态和审计从持久记录恢复。

长期、短期和探索性任务分别保留跨天检查点、截止条件和独立工作区。夜间按用户时区和租户策略执行，所用命令、真实路径、环境权限与预算都需匹配有效授权。主动暂停或人工介入时停发新动作，效果未知的旧操作保留待核对。

从提交任务到交付一次结果

  1. 接单。 客户端提交幂等键、工作区和输入快照版本。API 在同一事务写任务、预算预留和待发事件（outbox），提交后返回 202 与任务 ID。同一租户、项目、提交用户下，同键同载荷复用回执，同键不同载荷报冲突。
  2. 排队。 转发进程把 outbox 发到持久队列，收到发布确认且消息有路由后标记已发。消费者在数据库提交状态后确认消息，重复投递按事件 ID 去重。交互控制与批量计算使用独立队列；按租户配额和加权轮转分配，预留暂停、审批与取消的处理能力。RabbitMQ 发布与消费确认
  3. 选节点。 调度器匹配租户授权、地域、快照位置、环境、可用内存、GPU 型号和显存，在合适的节点间比较传输、等待与预计运行时间。代理主动连接并领取分配；中心以条件更新原子占用槽位、记录本次尝试和执行代号。设备在启动前把指令 ID 写入本机日志。
  4. 执行与取消。 企业自有设备只接受获准租户的项目。托管共享机器按任务使用独立的隔离运行环境，区分文件、进程、凭证与网络权限，设置资源上限；互不信任的客户代码使用隔离虚拟机。取消请求持久化，代理终止对应进程树并确认后释放槽位。
  5. 交付与对账。 结果先上传临时对象，校验后按任务、尝试和执行代号发布唯一终态。代理掉线后先查本机日志及既有回执。纯计算可按同一输入重新运行；部署、发布等有外部副作用的操作，仅在外部幂等键或执行证据可核实时重试。证据不足则标记“结果待核对”，值班人和用户均可追溯。

账号额度耗尽时，只暂停使用该凭据的相关任务。项目达到预算、执行槽满、上传限流分别显示原因和预计重试条件。CPU 队列增长时扩 CPU 执行池，GPU 满载时排队或转到获准的同型号设备。

公平调度的首个实现

设备上线时把可领取槽位归入区域和设备类型。每个池只维护有待处理任务的租户集合。调度器按租户权重轮询，每轮增加可用份额，取出该租户最早且资源匹配的作业，按所需槽位扣减份额；大作业可累积份额，单租户同时占用数另受套餐上限约束。按资源池分片，各调度实例在数据库中带版本领取同一分片。事务内复查租户配额、设备所有权和槽位余额，冲突则选下一个候选。记录作业未获分配的具体原因，便于区分排队、硬件不匹配和客户设备离线。

代码、会话与大文件如何交接

切换设备时，源端在已完成轮次封存 Git 基线、未推送对象、暂存层、工作树改动、获准新增文件、线程标识和路径映射。每个用户保有自己的工作副本。多人修改通过独立工作树、分支和合并请求汇合；发生同处冲突时保留双方版本供人工解决。

  • API 签清单，设备传字节。 控制服务按租户、对象、操作和有效期签发短时上传授权。客户端分片直传到本次上传独有的临时对象，记录校验和及分片回执。服务端核对大小、哈希、权限和对象版本后，在事务内发布不可变清单。下载按清单再次授权，跨租户隔离内容寻址和去重。S3 限时对象授权
  • 桌面在空闲时应用。 目标机先在暂存区校验签名及所有必需 LFS 对象，再核对工作区、IDE 和原生线程锁，原子切换并落本机回执。离线修改先封存，冲突保全。设备在新盘符下由终端适配器续接已经验证兼容的原生 CLI。Claude 的可恢复能力按独立兼容矩阵开放。
  • 企业数据留在哪里由项目决定。 获准上云的对象进入租户所属区域；限定内网的源码和原始会话留在客户执行端或其专有存储，云端仅接收获准元数据。LFS 缓存设容量水位，迁移依次复制、验哈希、切引用、清旧版，设置冷备和恢复演练。
  • 日报与记忆异步生成。 每个用户按本地日期生成一份日报，输入仅来自有权查看的事件。线程与轮次去重计量，跨设备活跃区间求并集，执行与排队时长分别汇总。晚到事件更新原日报；按项目归档决策、探索和原文引用，检索及打开来源时复核当前权限。扩展接入使用带版本的事件，支持回放重建。

Java 与 C++ 的分工由测量决定

先测用户从“切换设备”到“可以在终端继续工作”的时间。项目已有一组可复用的输入：64 MiB LFS 对象在 16 MiB 处断开，同配置第二次复验中，续传、复验、合并与自动应用共 4.812 秒，已就绪后再次扫描为 0.028 秒。这是旧版 Windows 回环实测。它给出了着手拆解的路径，Java 与 C++ 的收益有待同条件测量。2026-11-18 LFS 交接实验记录

剖析时看什么对应的工程动作
CPU 花在字节处理优先比较批量分块哈希、快照压缩或差量编码。Java 先用成熟库和流式缓冲，与 C++20 使用相同算法、块大小和线程数对照。已由原生 Git/LFS 完成的处理单独计时。
阻塞在网络、磁盘或锁记录磁盘读写量、下载字节、Git 子进程耗时、数据库锁等待和队列时间。分别试缓存复用、断点续传、批量查询、减少临界区或增加执行槽，将改动后端到端效果计入对照。
本机或 GPU 计算受限已有 C++/CUDA 工具作为受管作业运行，沿用退出码、日志、产物哈希及取消语义。候选快照加速器先做独立 C++ 子进程，用版本化请求传文件句柄或受限临时文件和偏移，分块返回校验结果；Java 负责权限、超时、取消和最终发布。

首个 Java/C++ 对照怎样判定

复用 64 MiB 续传夹具和 768 × 64 KiB 小文件夹具，另加 1 GiB 对象。Java 与 C++ 在同一主机、同一存储、同一压缩级别运行，分开冷缓存与热缓存、单任务与 8 任务并发。完成 JVM 预热后交替测试，至少取五批独立样本，每批至少 30 次。计入进程启动、IPC、I/O、校验和重试，保存 P50/P95、吞吐、CPU 秒、峰值内存、各阶段火焰图和原始结果。JFR 性能诊断 · LFS 端到端夹具 · 小文件合并夹具

建议采用门槛。 在目标负载下，若多批结果一致，端到端 P95 降低至少 20%，或相同吞吐下每任务 CPU 秒降低至少 30%，且内存符合节点预算、产物哈希与恢复结果一致，才灰度启用。注入超时、崩溃、磁盘满和坏分块；纯计算失败可切回 Java 从已校验检查点继续。门槛属于评审提案。

扩容、容灾与值班

首批商用租户放在一个区域的一个部署单元，API、网关和调度跨故障区部署，PostgreSQL 同步副本、队列多数派和对象存储跨区保护。租户目录记录所属区域、单元和路由版本，入口缓存映射。每个租户只有一个可写单元，常用请求可在该单元内完成。

  • 先扩无状态进程，再增加部署单元。 网关按连接和出口扩，API 按延迟和数据库预算扩，执行池按最老作业等待时间扩。按三故障区均摊时，失去任一区后其余两区仍须接住全量连接。举例，若实测每实例在目标延迟下安全承载 10,000 条连接，则每区 4 个、共 12 个可在失一区时留 80,000 条容量；10,000 是待测参数。
  • 控制数据库与热点。 任务列表索引以租户、项目、状态和时间为前缀，按游标分页；历史事件按日期分区，补读索引按租户、资源、序号建立。所有实例连接池总额预留故障切换和运维余量。单元在设计峰值下失一区无法满足 SLO，或大租户持续影响其他租户时，新增单元或把该租户独立部署。
  • 迁移租户。 按一致性快照复制租户数据并追增量，对齐对象清单和事件游标；短暂冻结该租户写入，排空任务分配，核对水位后切换路由版本，旧单元拒绝旧版本写入。解冻前可原路返回；解冻后先同步增量再回切。
  • 过载和依赖故障。 对单租户限制请求、订阅和上传带宽，超额请求返回 429 和重试时间。重连采用指数退避与随机抖动。Redis 中断时标记在线状态过期，限速补读持久状态；队列中断时保留已接单的 outbox，超过积压预算则暂停接新作业。数据库失去写入仲裁时停止授予执行权和审批。
  • 恢复与审计。 建议控制 API 月可用性目标 99.9%；单区故障要求已确认的控制事务零丢失。整区域灾难初始目标为 RPO ≤ 5 分钟、RTO ≤ 60 分钟。数据库做时间点恢复、对象按版本异地复制，演练同时核对两者恢复水位。晋升前隔离旧写端并提升执行代号世代，先与设备核对灾难窗口内未决指令，再恢复有副作用的操作。
  • 值班与单位成本。 请求、outbox、队列、代理回执使用同一追踪 ID；指标覆盖写入 P99、事件积压、重连、租约冲突、计费差异和出口成本。聚合指标用区域、单元、资源池和错误码做标签，单租户及任务编号留在受权限控制的日志与追踪中。SLO 错误预算消耗、最老交互任务超时、账单对账失败触发值班。每月按租户核算每活跃席位成本、每千次控制成本和每计算小时毛利，用于调整套餐和资源配额。

交付阶段完成条件与回退点
一 · 契约与只读影子固定当前 Web、设备活动、线程控制和签名交接格式，抽取脱敏样本。Java 导入时把原个人数据显式映射到所有者、租户和项目，保存原 ID 对照。影子实例仅比对读结果、事件顺序、哈希及权限；Python 继续独占真实写端。

三 · 跨设备与执行Java 代理在两台物理 Windows 机和两个真实 IDE 续接同一线程；验证多人独立工作树、冲突保全、Claude 能力范围、GPU 定向、夜间人工接管。用真实 iPhone Safari 在 VPN、Wi-Fi 和蜂窝下核对审批、后台恢复与可访问性。核对日报、项目记忆、套餐超额、退租导出及删除。
四 · 商用放量依次通过 1 千、1 万、5 万人在线混合压测及故障演练。交付仪表板、告警路由、恢复手册、版本兼容矩阵和可回退安装包。C++ 加速器独立灰度，可按设备或租户关闭。

放量前的验收表

  • 体验与容量。 用独立压测机产生前述 HTTP、WebSocket、心跳与作业负载，数据含大量小租户和一个占 20% 流量的租户。每档预热后稳态至少 60 分钟，另做 24 小时稳定性测试。建议区域内服务端 P95 读 ≤ 200 ms、写入受理 ≤ 300 ms，P99 分别 ≤ 500 / 800 ms；在线状态从提交至前台可见 P95 ≤ 1 秒。记录实际到达率、错误率、积压与资源余量。任务完成时间按 CPU、GPU 和外部模型分别统计。
  • 可靠性与公平。 模拟 20% 连接在 60 秒内重连、万人观看同一任务、400 台并行下载、队列重复投递、代理接单后断电及一个故障区退出。验收要求无跨租户读取、无双重审批、无重复结算，未决副作用可查证；受配额保护的其他租户在热点期间仍达到上述交互延迟目标。
  • 可核对的交付。 固定机器、代理和 CLI 版本、网络、输入、保留策略与队列设置。每阶段保存负载脚本、原始分位数、错误样本、计费对账和故障恢复时间，将未达标项记入项目实验记录。用试点的在线率、事件大小、任务时长和账单反算下一档部署规模。

团队分工与第一轮迭代

负责人先带队完成一条可演示的链路。甲、乙分别属于两家公司。甲在桌面提交项目的测试作业，执行端发起一个待审批的工具请求，甲用手机批准，设备回传退出码，账单出现一条用量记录。乙从列表、直链、订阅和下载入口均无法得知这个作业。实现这条链路后，各小组沿同样的契约扩展功能。

负责人 / 顺序领取的任务与输入提交评审时演示什么

先让数据库守住租户和唯一性

下表规定首批核心对象。tenant_id 来自认证上下文，所有时间按 UTC 保存；显示日报时才转用户时区。资源使用稳定 UUID。表间依赖用含租户的复合外键，保证即使应用参数传错也无法把甲公司的任务挂到乙公司的快照上。

project / membership项目主键 (tenant_id, project_id)。成员主键再加 user_id，包含角色、状态、授权版本。私人线程另存所有者和共享策略。资源查询先定位本租户，再检查项目及线程权限。

任务表迁移示例

以下为字段约束片段。迁移顺序为租户和成员、项目、快照、任务、尝试及事件。从 OIDC 身份识别的用户先映射为本地 UUID。冻结请求摘要的规范化算法，用同一规范比较 JSON 字段顺序不同的等价请求。

CREATE TABLE job (
    tenant_id uuid NOT NULL, job_id uuid NOT NULL, project_id uuid NOT NULL,
    actor_id uuid NOT NULL, snapshot_id uuid NOT NULL,
    request_key uuid NOT NULL, request_hash bytea NOT NULL,
    state text NOT NULL CHECK (state IN ('queued','assigned','running',
        'cancel_requested','reconciling','succeeded','failed','cancelled')),
    version bigint NOT NULL DEFAULT 1 CHECK (version > 0),
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, job_id),
    UNIQUE (tenant_id, project_id, actor_id, request_key),
    FOREIGN KEY (tenant_id, project_id, snapshot_id)
        REFERENCES snapshot (tenant_id, project_id, snapshot_id),
    CHECK (octet_length(request_hash) = 32)
);
CREATE INDEX job_project_page
    ON job (tenant_id, project_id, created_at DESC, job_id DESC);

接口契约与客户端错误处理

商业接口统一使用 /api/v2。旧版适配器继续识别原接口，其资源和个人空间经映射后才进入 v2 服务。OpenAPI 固定请求字段、成功响应、分页、错误枚举和示例，代理消息另有 schemaVersion。

接口实现及客户端行为
POST /projects/{p}/jobs需项目执行权限、Idempotency-Key 和已就绪快照。首次受理返回 202、固定 jobId 和查询地址。客户端提交前持久化键，发送超时继续复用原键，显式新作业才生成新键。
GET /projects/{p}/jobs/{j}返回状态、版本、当前尝试、更新时间和可执行动作。状态 GET 从授权上下文解析资源。界面遇到过期版本先刷新。
POST /projects/{p}/approvals/{a}/decisions提交 allow / deny、expectedVersion、幂等键；服务重新核对原连接、权限、版本和有效期。202 表示决定已持久化，执行端确认后更新回执状态。
POST /projects/{p}/jobs/{j}/cancel写入取消意图后返回 202。尚未派发可直接结束；已交给设备则显示“取消中”。终态竞争由状态机判定，刷新后呈现实际结果。
GET /projects/{p}/events按获准资源和 after 游标补读，支持 limit 和 nextCursor。WebSocket 握手后发相同资源的订阅及最后序号，接入时先订阅并缓冲，再查快照水位、按序合并，避免订阅建立时漏事件。

Java 事务、双击提交与可靠投递

这一节由后端工程师和负责人共同评审。一次事务只使用一个数据库连接。Spring 事务放在由容器调用的应用服务公共方法，仓储复用同一事务；向消息队列、对象存储和设备的网络调用在事务外进行。以下 Java 为接口级伪代码，方法名描述要由团队补齐的契约。Spring 声明式事务和代理边界

@Transactional(isolation = Isolation.READ_COMMITTED)
public AcceptedJob submit(Actor actor, ProjectId project, SubmitJob input, UUID key) {
    tenantContext.bindForTransaction(actor.tenant());
    access.requireCanRun(actor, project);
    var hash = requests.hashCanonical(project, input);
    var existing = jobs.findByRequest(actor, project, key);
    if (existing.isPresent()) return existing.get().receiptIfSameHash(hash);

    snapshots.requireReady(project, input.snapshotId());
    var job = Job.queued(actor, project, input, key, hash);
    if (!jobs.insertIfAbsent(job)) {
        return jobs.requireByRequest(actor, project, key).receiptIfSameHash(hash);
    }
    budgets.reserveOrThrow(job);       // 条件扣减可用额，同时登记预留
    events.appendAndEnqueue(job);     // 持久事件与 outbox 同一事务
    return job.acceptedReceipt();
}
  1. 并发判重。 实现 insertIfAbsent 时使用指向请求唯一键的 INSERT ... ON CONFLICT (...) DO NOTHING RETURNING job_id。两个请求同时查不到记录时，一个能插入，另一个在冲突结果确定后用下一条 SQL 从主库读取赢家。重复请求先验当前权限，再比摘要和初始回执。预留不足抛出会回滚的业务异常，事务整体撤销。PostgreSQL 冲突处理
  2. 金额和并发额度。 预算金额使用最小货币单位整数或固定精度小数，计量单位单列。原子更新中带“剩余额度足够”条件，检查受影响行数；预算账户、预留、用量按统一顺序取锁。终态事务只允许预留转结算或释放一次，重复设备回执读取前次结果。
  3. 投递。 转发器用短事务按可用时间领取一批待发事件，使用 FOR UPDATE SKIP LOCKED 并记录投递令牌和到期时间，提交后在事务外发布。发布确认及路由成功后，另开事务按该令牌标记 sent。令牌过期可重新投递；确认丢失会带来重复消息。消费者写 inbox 后与业务更新一同提交，再向队列 ack。PostgreSQL 行锁与 SKIP LOCKED
  4. 顺序与重试。 设备回执附 attempt、fence 和资源版本。旧版本回执留审计并拒绝覆盖新状态，遇到缺口按持久游标补读。暂时性错误采用有上限的退避；坏消息记录原 eventId、原因和版本后转入待处理队列。人工重放沿用原 eventId，按同一去重逻辑处理。

执行状态机与最难的断线窗口

由服务端提交状态转换。前端展示服务器返回的状态；代理只有提交事实和回执的权限。每次更新检查租户、任务、前置状态和版本，受影响行数为零时读取现状。每次有效转换递增版本，记录事件和证据。

起点 → 终点触发条件与必须同事务完成的事
queued → assigned有合格设备、租户额度和空槽。锁定槽位并插入唯一 attempt 与 commandId，记录设备、输入哈希、epoch、fence，通知代理。领取超时先查询设备日志。
assigned → running设备回报已启动、进程标识与输入快照相符。每次心跳仅续当前 attempt 的租约。相同 started 回执重复到达沿用已有事实。
queued → cancelled；assigned / running → cancel_requested尚未派发时原子取消、释放预留；已派发时记录取消意图，等待进程树退出的证据。取消与完成竞态以实际退出和发布记录核对，同一终态只结算一次。
running / cancel_requested → 终态按有效 attempt 验证退出码和产物清单，更新为 succeeded、failed 或 cancelled。发布结果、登记待结算事件并释放执行槽，界面随后读取终态。
assigned / running / cancel_requested → reconciling失联、命令结果未知或灾难恢复时记录原执行身份与动作。失联设备槽保持隔离。对账取得已完成证据时落终态；取得仍在运行的证据时回 running 或继续取消。
reconciling → queued确认旧动作未发生，或任务合同明确允许重复纯计算且可丢弃旧输出时，另建 attempt 并提升 fence。保留取消意图的作业优先完成取消和核对。外部发布效果未知时继续等待证据。

具体时序。 设备收到 commandId 后先在本机 SQLite 提交“已领取”。随后启动进程并追加进程标识及启动时间。如果设备恰在进程启动和日志写入之间断电，仅有“已领取”无法证明运行与否。重启后向原执行器查询同一外部键或核对产物；不具备核对能力的有副作用操作停在 reconciling。用户在操作页能看到命令、设备、最后证据及下一位处理人。

隔离迟到的旧进程。 每次转移控制权都提升 fence，灾备恢复时再提升独立 epoch；设备按二元组比较新旧，并持久化已见最高值。产物先写以 attempt 区分的临时位置，只有中心条件更新成功才能发布。对外部系统的写入还需要对方支持幂等键或显式核对。管理员人工解锁需提供原执行端已退出或外部动作已核实的证据，并写审计。

设备代理、网页与 C++ 怎样对接

设备工程师的首个版本

  1. 配对成功后把设备标识、租户绑定和证书引用写入本机受保护配置，密钥放操作系统凭据存储。设备能力上报 CPU、内存、GPU、可用空间、项目配置和代理协议版本。每个设备只领获准项目和运行配置。
  2. 把运行配置解析成固定可执行文件与参数数组，使用 ProcessBuilder 传参，校验工作区真实路径、符号链接或重解析点。分别限量读取 stdout / stderr，避免管道写满；输出按序分片并保留退出码。Windows 取消时跟踪整棵进程树，测试子进程晚退出、文件被占用和磁盘满。
  3. 快照按“临时下载 → 大小与哈希校验 → 记录回执 → 同卷原子发布”推进。将原路径切换的每一步写入本机恢复日志。对象收全前保留旧工作区，重新启动后读取恢复日志并核对本地状态。用包含未暂存与已暂存两种内容的同一文件验收。

前端工程师的同步规则

按 tenant / project / resource 存放缓存、最后确认序号和草稿。先显示权威初始快照，再应用序号连续的事件。小于等于已确认序号的事件丢弃；跳号时暂停应用后续事件，补读后按序恢复。撤销成员资格的通知关闭现有订阅；网关同时主动失效授权并周期复核。用户切换组织时取消旧请求，用上下文代号丢弃迟到响应。界面中的“已申请取消”与“已取消”分别绑定状态机。

C++ 原型只接一个可测函数

第一个原型限定为读取已封存文件、按固定块大小计算 SHA-256 清单。Java 提供本次工作私有目录中的输入与无冲突输出位置，通过受限的本机子进程传递路径；限制句柄、可访问目录、最大输入、并发、耗时与内存。控制消息用有界的长度前缀加 UTF-8 JSON，数据字节直接从文件读取。两端约定协议版本、字节偏移和长度均按字节计算，文件大小及偏移使用 64 位整数。版本不兼容时走 Java。

灰度步骤与值班动作

  1. 发布人。 数据库先做兼容扩展，部署能读旧格式的新消费者，再部署生产新事件的程序。先开放内部租户，再按试点、10%、50%、全量放开；每批至少覆盖业务高峰并核对用户体验、死信和账单。删除旧字段等所有旧读写端退出后另发迁移。
  2. 值班人。 接到“提交慢”的告警时，用 traceId 对照入口、连接池等待、数据库提交和 outbox 水位；“执行慢”则对照队列最老年龄、执行池资源和代理最后心跳。先记录影响的租户、地域与版本；限流热点、暂停批量报告或扩对应进程后复核 P99 与积压趋势。
  3. 负责人。 一旦发现跨租户可见、重复批准、重复计费或旧执行代号能发布，停止扩大灰度，关闭对应写入或订阅、保全审计，按租户核对已受影响记录，再决定回退或向前修复。单区域容量不足时按单元隔离影响；恢复后由第二人核对账本、产物和未决指令。
